# FastPKI — the PostgreSQL database

Everything FastPKI knows is in one PostgreSQL database: the certificates it issued, its
certificate authorities, users and roles, settings, templates, the audit log. This page is
for the person who looks after that database — how FastPKI connects to it, how to back it up
and restore it, how its schema changes between releases, and what every table is for.

Day-to-day work in the console is in [`admin-guide.md`](admin-guide.md). Running a standby
on a second host is [`high-availability.md`](high-availability.md). Replicating between data centers
is [`deployment.md`](deployment.md) §9.

PostgreSQL 17 is required. The container image and the native install both ship it, and
replication between data centers uses features that are new in 17.

## 1. What is in the database, and what is not

Almost everything is in the database. Five things are not, and a restore that ignores them
brings back a deployment that cannot work:

| Not in the database | Where it is | Why it matters |
|---|---|---|
| **Private keys** of every CA and every service credential | The PKCS#11 token (the bundled SoftHSM, or your HSM) | A restored database whose token is gone can still answer OCSP and serve certificates, but it cannot sign anything. Back the token up by your HSM vendor's procedure; for the bundled SoftHSM that is the `softhsm-tokens` volume. |
| **`PG_CONNINFO`** — how to reach the database | `bootstrap.conf`, or the environment | It is the one setting that cannot live in the database, because it is what finds the database. |
| **PostgreSQL's own TLS key** | `PG_TLS_DIR` (default `/var/pki/tls/pg`) | PostgreSQL reads its key from a file and cannot use a token. It is re-issued from the database's CA, so losing it costs a re-issue, not data. |
| **The token PIN** | `PKCS11_PIN_FILE` (default `/var/pki/tls/pin`) | Without it nothing can open the token. |
| **Kerberos keytabs** uploaded for a directory | `/var/pki/ms/<directory id>.keytab`; the database keeps only the path | Without them Windows clients cannot enrol with Kerberos. |

## 2. How FastPKI connects

Every FastPKI program reads `PG_CONNINFO`, a standard libpq connection string. The Docker
Compose deployment ships this one:

```
host=postgres port=5432 dbname=fastpki user=fastpki password=<generated>
sslmode=verify-full sslrootcert=/var/pki/tls/pg/ca.crt
target_session_attrs=read-write connect_timeout=5
```

- **`sslmode=verify-full`** — every connection is encrypted and checks the server's
  certificate and name. PostgreSQL is started with TLS on from the very first boot, before
  any CA exists.
- **`target_session_attrs=read-write`** — with two hosts listed (`host=a,b`), libpq picks
  whichever one currently accepts writes. That is how applications follow a promoted standby
  without being restarted (§7).
- **The password** is generated by `install.sh` and kept in `deploy/.env` as
  `POSTGRES_PASSWORD`.

### 2.1 The PostgreSQL server certificate

The database's TLS certificate goes through two stages:

1. **At install**, before any CA exists, `deploy/certgen.sh` makes a self-signed certificate
   so that the connection is encrypted from the start.
2. **Once you have a CA**, replace it with a CA-issued one. In the console: **Inventory →
   Issue Postgres certificate**, pick the issuing CA and the key type, **Issue**
   ([`admin-guide.md`](admin-guide.md)). On the command line:

   ```bash
   # Docker Compose (from deploy/)
   docker compose run --rm --no-deps --entrypoint fastpki-ca web \
       --config /app/config/bootstrap.conf pg-tls <ca_id>
   # Native (Alpine + OpenRC) and the cloud image — as the fastpki user, which owns the
   # token socket; as root the CA key cannot be opened and the command fails
   doas su -s /bin/sh fastpki -c \
       'fastpki-ca --config /etc/fastpki/bootstrap.conf pg-tls <ca_id>'
   ```

   It prints every name it put on the certificate. PostgreSQL picks the new certificate up
   within about 30 seconds, without a restart.

Two settings control it, both in the console's **Config** page:

| Setting | What it does |
|---|---|
| `PG_TLS_CA_ID` | The CA that issues the database certificate. **Set it**, or the nightly renewal job has no CA to ask and leaves the certificate to expire, saying so in its log. |
| `PG_TLS_SANS` | Extra names for the certificate. `postgres`, `localhost`, `127.0.0.1`, `PKI_DNS` and this host's `PG_BIND` are always included, so most deployments need nothing here. |

The daily renewal job (`certrenew` on Docker Compose, a CronJob on Kubernetes, a periodic
script on a native install) renews the certificate before it expires, using `PG_TLS_CA_ID`.
**Issuing from the console does not set `PG_TLS_CA_ID`** — set it yourself on the Config page
(Database area), or the certificate you just issued will not be renewed.

The certificate names `postgres`, `localhost`, `127.0.0.1`, `PKI_DNS`, this host's `PG_BIND`
and everything in `PG_TLS_SANS`. Its key is a file in `PG_TLS_DIR`, because PostgreSQL cannot
read a key from a token.

⚠️ **Use an RSA or EC CA for the database certificate.** A CA whose key is Ed25519, Ed448 or
ML-DSA is refused: PostgreSQL's connection security needs a signature with a separate hash,
which those algorithms do not have. Nothing is written when that happens.

## 3. Running SQL by hand

You rarely need to, but when you do:

| Deployment | Command |
|---|---|
| Docker Compose (from `deploy/`) | `docker compose exec postgres psql -U fastpki -d fastpki` |
| Kubernetes | `kubectl exec -it -n fastpki fastpki-node-0 -c postgres -- psql -U fastpki -d fastpki` — in a pair, the server whose database is the primary: `fastpki-node-0` unless it has been promoted away |
| Native (Alpine + OpenRC) and the cloud image | `doas su - postgres -c "psql fastpki"` |

⚠️ **Change FastPKI's data through the console or the CLI, not with SQL.** Many tables
have rules only the programs enforce — who may grant which role, which certificate a CA
serves, which values a setting accepts — and a hand-written SQL change skips all of them. Use
SQL to look.

## 4. The schema and how it changes

### 4.1 Where the schema is

`sql/createdb.sql` is the complete schema. A new database is created from it and is
immediately current. The version it records is kept in the `schema_version` table.

Every FastPKI program knows the **oldest** schema version it can work with. At startup it
reads `schema_version`, and if the database is older it refuses to start and names the
command to run. A **newer** database is fine — that is what lets old and new programs run
side by side during an update.

### 4.2 Applying a schema change during an update

A release that changes the schema ships the change as a numbered file in `sql/steps/`.
`deploy/schema-apply.sh` applies whatever is pending. **Run it before rolling out the new
programs**; the programs refuse an older schema, so doing it the other way round leaves
them restarting.

Every release carries every step, so you can update from any earlier release directly: the
script applies each step newer than the database, in number order. For example, a database
from v0.2.3 is at version 1, and updating it to v0.3.0 applies
`0002-acme-device-attestation.sql`:

```
== pending: 0002-acme-device-attestation.sql
== applying 0002-acme-device-attestation.sql
```

On a mesh node the script also regenerates the replication triggers, which it needs
`fastpki-mesh` for. Set `MESH_BIN` to the `fastpki-mesh` of the image you are updating
**to**, in the same command — it is part of every invocation below, and without it the
triggers are not regenerated:

```bash
cd deploy
# Docker Compose
MESH_BIN="docker compose exec -T web fastpki-mesh" \
PSQL="docker compose exec -T postgres psql -U fastpki -d fastpki" ./schema-apply.sh
MESH_BIN="docker compose exec -T web fastpki-mesh" \
PSQL="docker compose exec -T postgres psql -U fastpki -d fastpki" ./schema-apply.sh --check

# Kubernetes (deploy/k8s/apply.sh does this for you)
MESH_BIN="kubectl exec -i -n fastpki fastpki-node-0 -c web -- fastpki-mesh" \
PSQL="kubectl exec -i -n fastpki fastpki-node-0 -c postgres -- psql -U fastpki -d fastpki" ./schema-apply.sh
```

On a single deployment that is not part of a mesh, `MESH_BIN` can be left out.

On a native install and the cloud images, re-running `install-native.sh` applies pending
steps ([`admin-guide.md`](admin-guide.md) §14.4). To run the script by hand, connect the way
the installer does — as the `fastpki` database user, with the host, port, password and
`sslrootcert` from `PG_CONNINFO` in `/etc/fastpki/bootstrap.conf` (`127.0.0.1`, 5432 and
`/var/pki/tls/pg/ca.crt` when PostgreSQL runs on the node) — and tell it where the steps are
installed:

```bash
# as root; the values are the ones in PG_CONNINFO
PGPASSWORD='<password>' PGSSLMODE=verify-full PGSSLROOTCERT=/var/pki/tls/pg/ca.crt \
PSQL="psql -h 127.0.0.1 -p 5432 -U fastpki -d fastpki" \
MESH_BIN=/usr/local/bin/fastpki-mesh \
SCHEMA_STEPS_DIR=/usr/share/fastpki/sql/steps \
  bash /usr/share/fastpki/schema-apply.sh --check
```

`--check` applies no step, and exits with an error if any is pending. It still regenerates
the replication triggers, so `MESH_BIN` belongs in the command either way.
`rolling-update.sh`,
`deploy/k8s/apply.sh` and a re-run of `install-native.sh` run the schema step themselves, and
stop if it fails.

**Where to run it depends on the shape of the deployment:**

| Deployment | Run it on |
|---|---|
| One host | that host |
| A primary with a standby on a second host | **the primary only.** The standby receives the change by streaming. On the standby the script either finds nothing to do or fails with `cannot execute ALTER TABLE in a read-only transaction`. |
| Several data centers (mesh) | **every data center**, as you update it. Each database keeps its own `schema_version`. `MESH_BIN` names the `fastpki-mesh` of the image you are updating **to**, as the commands above show — see deployment.md §11.1. |

### 4.3 How a schema change is kept safe

A schema step must work with both the old and the new programs, because both run against the
database during an update. It happens in stages:

1. **Expand** — add the new column or table. The old programs ignore it.
2. **Migrate** — the new programs write both the old and the new shape.
3. **Contract** — once nothing old is running, a later step removes the old shape.

A change that cannot follow this pattern needs a maintenance window, and its step file says
so in its header.

## 5. Backups

A complete backup set has four parts:

| Part | How | How often |
|---|---|---|
| **The database** | `pg_dump` (below) | your normal database schedule |
| **The configuration backup** | console → **Backup**, or `fastpki-config backup` ([`admin-guide.md`](admin-guide.md)) | after changes to users, roles, profiles, templates or settings |
| **The token** | your HSM vendor's backup procedure; for SoftHSM, the `softhsm-tokens` volume | whenever a key is created |
| **A restore you have actually tested** | §6 | at least once |

The database dump includes the configuration, so the configuration backup is not needed to
recover the database. It is smaller, readable, and the quickest way back when someone
deletes a profile or a role by mistake.

### 5.1 Taking a database dump

```bash
# Docker Compose (from deploy/)
docker compose exec -T postgres pg_dump -U fastpki fastpki > /backup/fastpki-$(date +%F).sql

# Kubernetes
kubectl exec -n fastpki fastpki-node-0 -c postgres -- pg_dump -U fastpki fastpki > /backup/fastpki-$(date +%F).sql

# Native (Alpine + OpenRC) and the cloud image
doas su - postgres -c "pg_dump fastpki" > /backup/fastpki-$(date +%F).sql
```

The console makes a similar dump: **Backup → ⬇ Database backup** runs `pg_dump` on the server
with `--clean --if-exists --no-owner --no-privileges --no-subscriptions` and downloads it,
encrypted with a passphrase if you give one ([`admin-guide.md`](admin-guide.md) §13.2). The
console's **⬆ Restore database** takes such a file directly, up to 64 MB. To restore one from the
command line (§6), decrypt it first with
`fastpki-config decrypt-backup <file>.fpkibak --passphrase-file <file> --out <dump>.sql`
([`admin-guide.md`](admin-guide.md) §13.4).

⚠️ **A dump contains secrets.** It holds every console user's password hash, every user's
enrolment secrets (CMP, ACME, SCEP), directory service-account passwords, OIDC client secrets
and, in a mesh, the replication passwords — and a plain `pg_dump` also carries the replication
subscriptions with their connection strings. Store it like you store the token backup. It does
**not** contain any private key.

## 6. Restoring

⚠️ **A restore is a rollback in time.** Certificates issued after the dump still exist in
the world — on servers and laptops — but the restored database no longer knows them, so
OCSP answers `unknown` for them and they cannot be revoked. Prefer the most recent dump, and
re-issue anything issued since.

### 6.1 One host: stop, restore, start

On a single host a restore means downtime. Stop every FastPKI service except PostgreSQL,
recreate the database, load the dump, and start the services again:

```bash
cd deploy
# 1. Stop everything that uses the database. PostgreSQL and the token keep running.
docker compose stop web ocsp est acme cmp ms scep store auditfwd certrenew p11-tls

# 2. Recreate an empty database.
docker compose exec -T postgres psql -U fastpki -d postgres \
    -c 'DROP DATABASE IF EXISTS fastpki WITH (FORCE)' -c 'CREATE DATABASE fastpki OWNER fastpki'

# 3. Load the dump, in one transaction, stopping at the first error.
grep -viE '^[[:space:]]*(DROP|CREATE|ALTER)[[:space:]]+(SUBSCRIPTION|PUBLICATION)([[:space:]]|$)' \
    /backup/fastpki-YYYY-MM-DD.sql \
  | docker compose exec -T postgres \
      psql -U fastpki -d fastpki -v ON_ERROR_STOP=1 --single-transaction -q -f - >/dev/null

# 4. Start everything again.
docker compose up -d
```

Why step 3 looks like that:

- **The `grep`** removes replication setup (subscriptions and publications) from the dump.
  That belongs to one node and is set up again deliberately after a restore
  ([`deployment.md`](deployment.md) §9).
- **`--single-transaction` with `ON_ERROR_STOP`** means a failed restore changes nothing,
  instead of leaving half a database. Errors still print; `>/dev/null` only hides the rows
  psql echoes for the dump's own `SELECT` statements.

On a native install run the same statements as the `postgres` user
(`doas su - postgres -c "psql …"`), with `rc-service fastpki-<service> stop` and `start`
in place of the `docker compose` lines.

### 6.2 A primary and a standby: restore without downtime

With a standby on a second host, `deploy/db-restore-online.sh` restores without stopping the
service. A data center that is part of a mesh is restored with §6.3 instead. It restores into the standby while the primary keeps serving, then switches the two
over. Clients see one reconnect.

The script checks the database before it starts, and **refuses to continue when it holds
certificates newer than the dump** — which is the usual case, because the deployment has
been serving since the dump was taken. `--force` is what says you accept losing them. It
takes a dump made either way in §5: the plain `pg_dump`, or the console's backup.

**Docker Compose** — on the standby host:

```bash
cd deploy
PRIMARY_HOST=<primary address> ./db-restore-online.sh /backup/fastpki-YYYY-MM-DD.sql --force
```

**Native or cloud** — on the standby host, as root:

```bash
PRIMARY_HOST=<primary address> /usr/share/fastpki/db-restore-online.sh /backup/fastpki-YYYY-MM-DD.sql --force
```

**Kubernetes** — on any machine with `kubectl` for the cluster, naming the standby's pod:

```bash
cd deploy
NAMESPACE=fastpki ./db-restore-online.sh /backup/fastpki-YYYY-MM-DD.sql fastpki-node-1 --force
```

On Docker Compose and native, the script asks you to stop the primary's database on the other
host when the restore is loaded, and waits until it has stopped. On Kubernetes it stops the
old primary's database itself.

When it finishes, **the roles have swapped**: the standby is the primary. On Kubernetes the
script then re-copies the old primary's database from it, which makes that server its standby.
On Docker Compose and native it prints the commands to run on the old primary's host
([`high-availability.md`](high-availability.md) §6). Add `--no-rebuild` to leave that step to you.

If a restore is interrupted, check `SHOW transaction_read_only` on the node it was restoring.
The script sets it to hide that node from applications while it works; a leftover value
keeps the node hidden after a restart.

### 6.3 A data center in a mesh

In a mesh, most of a data center's database is a copy of rows the other data centers also
hold, and their copies are newer than your dump. Loading the dump as in §6.1 and replicating
again would keep the dump's old rows: a certificate revoked elsewhere after the dump would
stay valid on the restored data center, and a user or role grant deleted elsewhere would come
back there. The replication links also have to be rebuilt, because the other data centers
remember positions in the database that was replaced.

So a restored data center takes its replicated rows **from the other data centers**, and
from the dump only what they do not have:

- its own settings, audit log and discovery results, which are never replicated;
- its references to the keys in its own token;
- certificates, revocations and renewals it recorded that never reached another data center.

Any other change the data center made while it was cut off from the others is not recovered.

`fastpki-mesh --restore` writes the SQL for this as one file. You run the file several times,
each time telling `psql` which step to run and which data center it is connected to. Without
those two variables the file does nothing.

At least one other data center must be running. **Do not restore every data center from one
dump** — that makes every node claim the same history as its own.

The steps below restore data center `2` of a Docker Compose mesh, from `deploy/` on each
host, with the same `topology` file the mesh was set up with ([`manual-procedures.md`](manual-procedures.md)
§8). On a native or cloud node, run `fastpki-mesh` and `psql` as in manual-procedures.md §8.

```bash
# Generate the file once, and copy it to every data center.
docker compose run --rm --no-deps --user 0:0 -v "$PWD/topology:/topology:ro" \
    --entrypoint fastpki-mesh web --topology /topology --node 2 --restore > restore-2.sql

# On each host: set NODE to the index of the data center you are typing on — 2 on the
# data center being restored, 1 or 3 on the others — then define the step command.
NODE=2
step() {
  docker compose exec -T postgres psql -U fastpki -d fastpki \
      -v node="$NODE" -v step="$1" < restore-2.sql
}
```

If the dump comes from an older release than the one now installed, run
[`schema-apply.sh`](../deploy/schema-apply.sh) (§4.2) on data center 2 between steps 3
and 4.

1. **On data center 2**, stop every service that uses the database
   (§6.1 step 1). If its database still exists, run `step detach` there.
2. **On every other data center**, run `step detach`. This removes their replication links
   with data center 2. They keep serving.
3. **On data center 2**, recreate the database and load the dump — §6.1 steps 2 and 3.
4. **On data center 2**, run `step rebuild`. It sets aside what only the dump has, empties the
   replicated tables, and copies them from every other data center. It waits until the copy
   has finished, printing progress every 30 seconds.
5. **On every other data center**, run `step resubscribe`.
6. **On data center 2**, run `step finish`. It puts back the key references, certificates,
   revocations and renewals it set aside, and they replicate to the other data centers.
7. **On data center 2**, start the services: `docker compose up -d`.

Check every data center with `--verify` and compare certificate counts
([`deployment.md`](deployment.md) §9.2).

A step run on the wrong data center, or out of order, stops with a message saying what to run
instead. `rebuild` can be run again if it stopped part-way. `resubscribe` refuses to run twice
on the same data center: if it says the subscription already exists and you did not run it
there before, `detach` was skipped on that data center — run `step detach` there, then
`step resubscribe` again.

## 7. A standby on a second host

A primary PostgreSQL on one host can stream every change to a standby on a second host. If
the primary host fails, you promote the standby and the applications follow it on their next
database statement — no restart, no virtual IP.

```bash
cd deploy
./ha-join.sh <primary-address> primary-ca.crt   # on the new standby host, once
./pg-promote.sh                                 # on the standby host, after stopping the failed primary
```

On a native or cloud host, the join is one command from your own machine, over SSH to both
hosts ([`high-availability.md`](high-availability.md) §3):

```bash
deploy/ha-join-pair.sh --primary alpine@<primary> --standby alpine@<standby>
```

The promotion is `doas /usr/share/fastpki/pg-promote.sh` on the standby, after stopping the
failed primary.

⚠️ **This protects the database, not signing.** A promoted standby can sign only with CA
keys that were created replicable and copied into its own token beforehand
([`high-availability.md`](high-availability.md)). The full setup, failover drills and how to restore the pair
afterwards are in [`high-availability.md`](high-availability.md).

## 8. Several data centers

Each data center has its own PostgreSQL. They copy selected tables to each other with
PostgreSQL logical replication, so a certificate issued in one data center is known to
all. `fastpki-mesh` generates the replication setup; do not write it by hand.

What this means for the tables is in §9, in the **Copied between data centers** column.
Three consequences an administrator notices:

- **Settings are per data center.** The `config` table is not copied, because it holds each
  node's own identity — the data center id, bind addresses, TLS paths. Certificate profiles
  are **not** settings in this sense: they have their own `cert_profiles` table and that
  table **is** copied, so a profile edited in one data center reaches the others.
- **The audit log is per data center.** Each node keeps, verifies and forwards its own.
- **Private key locations are per data center.** A CA registered everywhere signs only where
  its key is in the local token.

Setting it up, adding and removing data centers and checking that they agree are in
[`deployment.md`](deployment.md) §9; the design is in [`architecture.md`](architecture.md) §8.

## 9. Table reference

**Copied between data centers** means the table is part of mesh replication. "No" means
each data center keeps its own. A standby on a second host always has an exact copy of
everything, whatever this column says.

### 9.1 Certificates and certificate authorities

| Table | What it holds | Copied between data centers |
|---|---|---|
| `certs` | Every certificate FastPKI issued or registered — leaf certificates **and** CAs. A CA row has `is_ca` set, its `id`, display `name`, `ca_enabled`, and `private_key` (the `pkcs11:` location of its key in this node's token). `status`, `revocationDate` and `revocationReason` record revocation. `owner` is who requested it, `cert_id` marks a certificate a service uses (a listener or an RA credential). `fp_sha1` and `sans` are read off the certificate when the row is written, so the console can find it by thumbprint or by a name that is not its CN. | Yes, except `private_key` |
| `cert_uris` | The URI names inside each certificate, so the certificate store can search by them. | Yes |
| `crls` | CRLs published for a CA: CRLs imported for an offline root (`fastpki-ca import-crl`), and the latest CRL of each CA a node holds the key for, so other data centers can serve it while that node is down. | Yes |
| `foreign_anchors` | Other organisations' CA certificates registered for cross-signing. | Yes |
| `ca_xcep_uris` | The enrolment addresses each CA advertises to Windows clients (MS-XCEP). | Yes |
| `datacenters` | The data centers of a mesh: each one's serial prefix, public address and replication connection. A single deployment has one row. | Yes |
| `p11_transport` | Each host's certificates for the encrypted token tunnel used when copying keys between hosts. | Yes |
| `node_status` | What each host reports about itself for the console's Replication page: which keys its token holds, its database connection and certificate, the replication it sees, and the result of its last key sync. Each host rewrites its own row about once a minute. | Yes |
| `node_sync_requests` | A request, made from the Replication page, that a host run key sync now. | Yes |

### 9.2 Enrolment

| Table | What it holds | Copied between data centers |
|---|---|---|
| `keys` | Per-user enrolment secrets: the CMP shared secret, the ACME External Account Binding key and the SCEP challenge password, one row per user and protocol. | Yes |
| `cert_req_ids` | CMP transaction identifiers, used while a CMP exchange is in progress. | No |
| `nonces`, `accounts`, `orders`, `authorizations`, `challenges` | ACME: one-time nonces, client accounts, orders and their validation state. | No |
| `scep_challenges` | SCEP one-time challenge passwords. | No |
| `acme_device_tickets` | ACME device-attestation tickets: one-time, each used by the node that issued it, with the attested serial number and certificate once used. | No |
| `acme_device_serials` | Device serial numbers an MDM fleet enrols by over ACME device attestation, each with its CA, owner and profile. | Yes |
| `scep_pending` | SCEP requests waiting for manual approval. | No |

### 9.3 Users, roles and sign-in

| Table | What it holds | Copied between data centers |
|---|---|---|
| `web_users` | Every account: username, primary role, password hash (a directory or SSO account has no usable local password), whether a password change is forced, which provider authenticates it, and the email address expiry emails go to. | Yes |
| `roles` | Role names, descriptions, and the per-role issuance limits (`max_certs`, `max_cn`, `max_san`). | Yes |
| `role_permissions` | What each role may do: one row per permission and scope ([`rbac.md`](rbac.md)). | Yes |
| `subject_roles` | Extra roles given to a user or to a directory group. | Yes |
| `web_sessions` | Console sessions. The token itself is never stored, only its hash. | No |
| `auth_providers` | The directories and identity providers users sign in through: id, kind, display name, enabled, order. | Yes |

## 10. Housekeeping

FastPKI removes some short-lived rows itself: expired ACME nonces and orders (with their
authorizations and challenges), and expired console sessions.

It keeps everything else, on purpose:

- **Certificates are never deleted**, including expired and revoked ones.
- **The audit log only grows, and cannot be trimmed.** Verification always starts from its
  first entry, so once rows are deleted `fastpki-audit verify` fails for good, and `sign` and
  both signed exports (command line and console) refuse to run.
- **Discovery results** accumulate with every scan.

PostgreSQL's automatic vacuum is enough for these tables; FastPKI needs no vacuum schedule
of its own.

### 10.1 Checking replication

```sql
-- on a primary with a standby: the standby should be listed with state 'streaming'
SELECT client_addr, state, replay_lag FROM pg_stat_replication;

-- on a mesh node: one row per peer subscription, each with a recent latest_end_time
SELECT subname, received_lsn, latest_end_time FROM pg_stat_subscription;
```

`fastpki-mesh --verify` checks that a mesh node has every publication, subscription and
trigger it should ([`deployment.md`](deployment.md) §9).

## 11. When something is wrong

| What you see | Cause and fix |
|---|---|
| A service restarts in a loop right after an update, and its log names a schema version | The schema is older than the programs. Run `schema-apply.sh` (§4.2). |
| `cannot execute ALTER TABLE in a read-only transaction` from `schema-apply.sh` | You ran it on a standby. Run it on the primary (§4.2). |
| Services cannot connect: `certificate verify failed` | The database certificate is not trusted by `sslrootcert`, or does not name the host in `PG_CONNINFO`. Re-issue it with the right names (§2.1). |
| The database certificate expired | `PG_TLS_CA_ID` is not set, so nothing renewed it. Set it and issue a new certificate (§2.1). |
| Applications stay on a dead primary after promotion | `PG_CONNINFO` lists only one host. It must list both, with `target_session_attrs=read-write` (§2, [`high-availability.md`](high-availability.md)). |
| A user exists in one data center but not another | Mesh replication has stopped. Check `pg_stat_subscription` (§10.1). |
| A profile works in one data center and not another | `cert_profiles` is copied between data centers, so the copy has stopped. Check `pg_stat_subscription` (§10.1). |
